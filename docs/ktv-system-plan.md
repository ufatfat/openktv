# OpenKTV 单实例系统方案

## 1. 产品边界

OpenKTV 面向家庭、工作室和小型聚会场景。一套部署只有一个播放实例、一份全局曲库和一份全局点歌队列。系统不包含房间、包厢、房主、成员、会员、计费、酒水或门店管理。

系统由三个用户界面和一个本地服务组成：

- `/`：手机、平板和电脑使用的点歌与控制台。
- `/player`：电视或投影仪使用的全屏播放端。
- `/admin`：曲库扫描、歌曲维护和设备状态管理。
- `server/`：SQLite 持久化、全局队列、播放状态、媒体服务与 WebSocket 同步。

## 2. 第一阶段功能

### 曲库

- 按歌名、歌手和语言搜索。
- 扫描本地媒体目录，识别 mp4、webm、mp3、m4a、wav、ogg 和 flac。
- 读取与媒体同名的 `.lrc` 文件。
- 手工添加歌曲元数据，删除错误条目。
- 标记资源是否可播放。

### 点歌与控制

- 点歌、置顶、上移、下移和删除。
- 播放、暂停、切歌、静音和音量控制。
- 当前播放状态和队列落入 SQLite，重启后恢复。
- 所有打开的控制端通过 WebSocket 接收同一份状态。

### 播放端

- 播放本地视频或音频，支持浏览器原生 Range 请求。
- 显示同步歌词、当前歌曲和下一首。
- 播放结束后自动切换下一首。
- 浏览器阻止自动播放时，明确显示开始播放按钮。

### 运维

- 健康检查。
- Docker Compose 一键启动。
- 数据库、媒体目录使用宿主机卷持久化。
- 附带可播放的系统试音文件，用于首次部署验收。

## 3. 不在第一阶段内

- 房间或包厢系统。
- 用户注册、会员、支付和社交关系。
- 在线商业曲库和未经授权的媒体抓取。
- 专业麦克风低延迟混音、啸叫抑制和演唱评分。
- 多门店、POS、酒水及服务员呼叫。

专业麦克风链路应交给声卡、调音台或后续的原生播放代理；Web 层只负责点歌、媒体播放和控制状态。

## 4. 技术架构

```text
点歌台 / 管理台 / 大屏播放器
            │ HTTP + WebSocket
            ▼
       Node.js 本地服务
       ├── 全局播放状态
       ├── 全局点歌队列
       ├── SQLite 数据库
       ├── 媒体目录扫描
       └── 音视频 Range 服务
            │
            ▼
      本地硬盘 / NAS 挂载目录
```

前端保留现有 React/Vinext 工程。后端仅依赖 Node.js 内置 SQLite 和 `ws`，避免引入独立数据库服务。生产部署由两个容器组成：前端容器监听 8787，后端容器监听 8091。

## 5. 核心数据

- `songs`：歌曲、歌手、语言、分类、媒体路径、歌词路径和时长。
- `queue_items`：全局队列及顺序。
- `playback_state`：当前歌曲、播放状态、进度、音量、静音、原伴唱和升降调。

所有写操作在服务端串行完成，并在成功后广播最新快照。浏览器不再作为状态真源。

## 6. 验收标准

1. 新环境执行 `docker compose up --build` 后可以打开三个页面。
2. `/api/health` 返回数据库与服务正常。
3. 系统试音可以加入队列并在 `/player` 播放。
4. 两个浏览器窗口的点歌队列和播放状态实时一致。
5. 重启后歌曲、队列和播放设置仍然存在。
6. 把媒体文件放入媒体目录并执行扫描后，可以被搜索和播放。

## 7. 后续演进

第二阶段再加入媒体转码任务、拼音搜索、封面提取、缓存预热、原伴唱双音轨、升降调处理、本地播放代理和设备监控。正式运营前必须解决歌曲、MV、伴奏和歌词的授权问题。
